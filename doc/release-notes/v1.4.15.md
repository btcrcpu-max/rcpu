# RCPU Core v1.4.15 Release Notes

**No consensus change.** Block validation, difficulty, activation heights and
all historical blocks are unchanged. Nodes, pools and miners may upgrade at any
time; v1.4.14 and v1.4.15 agree on every block.

## qhash second-algorithm path removed

The original dual-algorithm design selected the second PoW algorithm through
the `fDualAlgoEtchash` flag: `true` routed bit-30 blocks to Etchash, `false`
routed them to the legacy qhash (qPoW) verifier. qhash was assessed as
cryptographically unsuitable and was replaced by Etchash **before** the
dual-algo fork went live, so every deployed network has always used Etchash:

- mainnet/testnet: bit-30 blocks exist from height 21,000 and all of them are
  Etchash;
- regtest: bit-30 blocks are Etchash from height 150.

`fDualAlgoEtchash` was therefore always `true` on live chains, which makes the
qhash code unreachable dead code. v1.4.15 removes it outright:

- `src/crypto/qhash.{h,cpp}` are deleted;
- `PowAlgo` has two members (`RandomX`, `Etchash`) instead of three;
- `CheckProofOfWorkQHash` and the `else` branch of the dual-algo dispatch are
  gone;
- `getblocktemplate` no longer has a qhash output branch (the template for a
  bit-30 block is always the Etchash template);
- `generatetoaddress` still rejects `algo="qhash"` with the same
  `RPC_INVALID_PARAMETER` error, now because the algorithm does not exist
  rather than because the flag is off.

Removing dead code reduces the attack surface (one fewer hash implementation
linked into every binary) without changing any validation result. Because no
qhash block ever existed on mainnet, testnet or the existing regtest chains,
historical replay is byte-identical.

**Upgrade note for custom regtest chains**: a chain that was somehow mined
with the non-Etchash (qhash) path cannot be validated by v1.4.15. No such chain
is known; the flag only existed in builds that predate the Etchash switch.

## `computerandomxhash` dual-algo dispatch fix

`computerandomxhash` computes the RandomX hash/commitment of a header for
pools. It previously routed **every** bit-30 header to the Etchash verifier.
That is wrong for headers below the dual-algo activation height (and for
headers whose parent is unknown), where consensus ignores bit 30 and validates
the block as RandomX. Those headers were therefore hashed with the wrong
algorithm and the returned `hash`/`commitment`/`hash_verified` were
meaningless.

v1.4.15 routes by height exactly like `GetPowAlgoForHeader`: bit-30 headers at
or above `nDualAlgoActivationHeight` use Etchash (where the Etchash result is
the commitment), everything else uses RandomX (where the commitment is the
RandomX commitment). Headers with an unknown parent keep the RandomX path
because no Etchash epoch can be derived.

The RPC result documentation now also lists the `hash_verified` field that the
implementation has always returned.

## Verification

- Unit tests: full `test_bitcoin` suite (718 test cases) passes, including
  `dualalgo_tests`, `pow_tests` and `bip324_tests`.
- Functional tests on rcpuregtest: `feature_dualalgo_count_cache.py`,
  `feature_rbf_rcpu.py`, `wallet_bumpfee_ct.py` and the new
  `rpc_computerandomxhash_dualalgo.py` all pass.
- `rpc_computerandomxhash_dualalgo.py` asserts the commitment/hash relation on
  four paths: pre-activation RandomX, pre-activation bit-30 (RandomX path),
  post-activation Etchash (`commitment == hash`) and post-activation RandomX.
- Mainnet full-chain submitblock replay (genesis..tip 28,183) on an instrumented
  build: 0 rejected blocks, tip hash matches source node, and
  `CheckProofOfWorkEtchash` was invoked 9,894 times (all mode=0 full
  verification), proving the Etchash path is exercised and unchanged after
  qhash removal.

## Upgrade

Download v1.4.15, verify `SHA256SUMS.txt.asc` with the RCPU release key, and
restart. There is no activation height for this release.
