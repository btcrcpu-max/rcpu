# RCPU Core v1.4.16 release notes

v1.4.16 is a small hardening release: four commits, five files, +27/−45 lines.
It follows the v1.4.14/v1.4.15 audit-remediation line and does not change the
CT rules or the dual-algorithm parameters.

## Consensus

### BIP9 activation thresholds corrected

`nMinerConfirmationWindow` is 4032 blocks (14 days at 5-minute spacing), but the
activation thresholds still carried Bitcoin's 2016-block values. The effective
threshold was therefore ~45% (mainnet/signet) and ~37.5% (testnet) instead of
the documented 90% / 75%.

- 90% chains: `1815 -> 3629` (`ceil(0.9 * 4032)`), three chain classes.
- 75% chains: `1512 -> 3024` (exactly 75% of 4032), two chain classes.
- Regtest (108/144) was already consistent and is unchanged.

No immediate consensus impact: `TESTDUMMY` is `NEVER_ACTIVE` and `TAPROOT` is
`ALWAYS_ACTIVE`, so no deployment currently counts version bits. The change
only affects any future soft fork.

### Non-genesis checkpoints removed

The 15-entry checkpoint table made `GetLastCheckpoint()` return the highest
known checkpoint during headers-first sync, and the height-only comparison in
`ContextualCheckBlockHeader` then rejected every block below that height with
`bad-fork-prior-to-checkpoint`. New nodes could not complete IBD.

The table now contains genesis only. `nHeight < 0` can never be true, so no
block is rejected by the checkpoint guard.

**Trade-off:** checkpoints no longer protect against deep reorgs below their
former heights. Protection now rests on `nMinimumChainWork` and
`defaultAssumeValid` (anchored at height 21,000). This release does not add a
replacement checkpoint mechanism; do not re-add checkpoint data without first
making the guard fork-relative, or IBD will stall again.

### H-1 dual-algorithm lateness fix (activates at 29,909)

The H-1 re-anchor rule has been present since v1.4.14 (not introduced here).
At height 29,909 the rule activates on **both mainnet and testnet** — the two
networks share the same height.

This is a hard fork. **All nodes, pools and miners must run v1.4.14 or newer
before height 29,909.** v1.4.13 and older nodes will diverge at that height.

## Build, CI and release

- `workflow_dispatch` is allowed for CI so a release manager can re-run the
  unit suite without a dummy commit.
- The release tag guard and the release signing steps are **fail-closed**:
  an unsigned tag, a tag signed by an unexpected key, or a missing
  `GPG_PRIVATE_KEY` aborts the release instead of warning.
- Windows Authenticode signing remains conditional on
  `WINDOWS_SIGNING_CERT`; without it the artifacts are published with an
  explicit `-unsigned` suffix.

## Verification

Node binaries are listed in `SHA256SUMS.txt` with a detached
`SHA256SUMS.txt.asc`. The GUI AppImage has its own `.sha256` and `.asc`.

```
gpg --verify SHA256SUMS.txt.asc SHA256SUMS.txt
sha256sum -c SHA256SUMS.txt --ignore-missing
git verify-tag v1.4.16
```

The v1.4.16 tag published on 2026-11-18 was **not** PGP-signed; the artifacts
are checksum-signed but tag provenance is not. Prefer a signed tag for any
deployment that pins by tag.

## Compatibility

- Upgrade from any v1.4.x: no reindex required.
- Nodes older than v1.4.14 must upgrade before height 29,909.
- No RPC or wallet format change.
