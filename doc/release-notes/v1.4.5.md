# RCPU Core v1.4.5 Release Notes

> **Status:** DRAFT — not tagged. `nCTStrictRulesHeight` is frozen at
> **27,326** from observed tip 25,310 + 2016; re-check `getblockcount` before
> tagging and update the three consensus/doc files if the tip has moved.

## Security fixes

- **H-1 (immediate): v3 transactions must not use `SIGHASH_SINGLE` or
  `SIGHASH_SINGLE|ANYONECANPAY`.** Under the legacy CT serialization the
  signature did not commit to the Pedersen commitment, `nNonce` or
  `vchRangeproof` of the signed output; a third party could rewrite or freeze
  the output after signing. The wallet, RPC, PSBT and hardware-wallet paths must
  not construct v3 SINGLE signatures after this release. Explicit v3 SINGLE is
  rejected as well, because the other outputs of a v3 transaction may be
  confidential and are not covered by SINGLE. This is a **tightening rule** and
  applies as soon as the upgraded node is running; coordinate the upgrade before
  any v3 SINGLE transaction is expected on-chain.
- **M-1 (from the scheduled CT strict height):** a confidential output must
  carry a non-null nonce that parses as a real curve point (`0x03` compressed
  pubkey or `0x04` x-only key). A null nonce or an off-curve `0x03`/`0x04`
  value was accepted before, but the recipient could not rewind it, allowing
  payment forgery. Explicit/fee outputs keep the historical `0x03`/`0x04`
  shape rule.
- **H-2 (CI):** `make check`, functional tests and fuzz tests no longer swallow
  failures with `|| echo`; `make distdir` is restored with the correct
  `rcpu-$HOST` directory.
- **M-3 (DoS):** bit-30 Etchash blocks are now fully PoW-checked in
  `CheckBlock()` before transaction/merkle parsing. A forged `hashRandomX`
  header can no longer force the expensive validation work first.
- **M-4 (P2P):** mandatory script failures are classified as
  `TX_CONSENSUS` again (retry without the non-mandatory flags), and
  `MaybePunishNodeForTx()` assigns the 100-point penalty for invalid
  transactions and invalid orphans.
- **M-5 (wallet privacy):** encrypted wallets no longer persist plaintext CT
  amounts in `ct_unblind_*` / `vout_amount_*`; legacy entries are purged at
  wallet load and again on lock/unlock. Wallet encryption protects keys, not
  `mapValue`, so the old cache leaked every CT amount to anyone with a copy of
  `wallet.dat`.

## Consensus changes and activation

**H-1 is immediate and is not height-gated.** v3 `SIGHASH_SINGLE` and
`SIGHASH_SINGLE|ANYONECANPAY` are rejected as soon as the upgraded node is
running, regardless of `nCTStrictRulesHeight`.

M-1 and M-2 are **scheduled consensus changes**, gated by
`Consensus::Params::nCTStrictRulesHeight`.

| Item | Value |
|---|---|
| Observed mainnet tip | **25,362** (2026-11-08; verify with `getblockcount`) |
| `nCTStrictRulesHeight` | **27,326** |
| Calculation | **25,310 + 2,016** (freeze tip; Path-A convention) |
| Buffer at observed tip | **1,964 blocks / ~6.8 days** |
| Indicative activation | **~2026-11-15** (hashrate-dependent) |

- `27,326` is the frozen candidate for this draft. It was calculated as
  `25,310 + 2016` when the tip was 25,310; the current tip 25,362 leaves 1,964
  blocks (~6.8 days). Before tagging, check `getblockcount` again on the
  release node. If the tip has moved further, recompute `final_tip + 2016`
  (or `final_tip + 2880` for a ~10-day window) and update
  `src/kernel/chainparams.cpp`, `doc/consensus-params.md` and these release
  notes in the same commit.
- Record the final values in the release notes: the tip at freeze time, the
  formula used, and the estimated activation date. Do not publish a tag with
  a stale height.
- Testnet and regtest use `0`; other networks default to `INT_MAX` (never).
- Before the height, the old behavior is preserved: M-1 only checks the
  historical `0x03`/`0x04` shape for non-null nonces, and M-2 still rejects
  explicit zero values via `ExplicitCommit(0)`.
- At/after the height:
  - a confidential output with a null or off-curve nonce is rejected with
    `bad-ct-nonce-missing` / `bad-ct-nonce-point`;
  - explicit zero inputs/outputs are treated as the Pedersen identity and are
    skipped in the value tally;
  - a zero **fee** output remains invalid.

**M-2 is a relaxation of the old rule.** It must only activate at a coordinated
height; the scheduled height exists specifically to avoid an unannounced
hard-fork split between upgraded and non-upgraded nodes.

## Wallet / RPC behavior changes

- After upgrading, an **encrypted** wallet that is locked will show CT
  amounts as zero until it is unlocked and the outputs are re-unblinded. This
  is the expected trade-off for no longer storing plaintext CT amounts on
  disk. Unencrypted wallets keep the existing cache behavior.
- V3 `SIGHASH_SINGLE` will fail in `signrawtransactionwithwallet`, PSBT
  signing and any external signer that does not implement the new rule. Use
  `SIGHASH_ALL` (the wallet default) or `SIGHASH_DEFAULT` for taproot.

## Build, supply chain and reproducibility

- **M-6:** startup runs a fixed RandomX A2000 vector and refuses to start if
  the linked `librandomx` is not the RCPU variant (custom Argon salt). This
  adds a one-time ~256 MB RandomX cache allocation during startup; it is
  released immediately after the check.
- **M-7:** release workflows SHA256-check the pinned RandomX source tarball
  before extracting the shipped `randomx.h`.
- **M-8:** the Linux package fails if any of `rcpud`, `rcpu-qt`, `rcpu-cli`,
  `rcpu-tx`, `rcpu-wallet` is missing or empty.
- **M-9:** release tag builds require a valid signature from the documented
  RCPU key (`VALIDSIG 934D5BC95DD4B3ACFEF521B9547633501FE4B8EE`); signing is
  forced to that fingerprint and the detached signature is verified. An
  unsigned release fails instead of publishing an unsigned `.asc`.
- **M-10:** `make -C depends` now actually builds and installs the `randomx`
  package (with `custom_configuration.patch`), so the reproducible/guix build
  path matches `configure`'s hard RandomX requirement.

## Upgrade notes

- This release contains a **consensus tightening** (H-1) and a **scheduled
  consensus change** (M-1/M-2). All nodes, pools, explorers and wallet
  backends should upgrade before the published activation height.
- **Mixed-version warning:** v1.4.4 still accepts v3 SINGLE transactions (and
  null/off-curve nonces before the strict height). If an old node mines or
  relays such a transaction, upgraded nodes will reject the block/transaction;
  coordinate the upgrade rather than assuming a soft-fork transition is
  automatic.
- **M-4 peer penalties:** a peer that supplies a consensus-invalid transaction
  can now be banned (100 points). Old wallet software that constructs invalid
  CT/nonce/SINGLE transactions must be upgraded before pointing it at a
  v1.4.5 node.
- Back up `wallet.dat` and the passphrase before upgrading an encrypted
  wallet. M-5 removes legacy plaintext CT metadata; this is a one-way cleanup
  and the removed values are recomputed from the chain while unlocked.
- If you use a hardware wallet or external PSBT signer, update its v3
  SIGHASH policy before signing any v3 transaction.
