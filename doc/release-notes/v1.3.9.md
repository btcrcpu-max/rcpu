# RCPU Core v1.3.9 Release Notes

> **Status:** released (tag `v1.3.9`). This is a **hardening release**, not a
> consensus change. Every rule that decides whether a block is valid, and every
> difficulty calculation, produces exactly the same result as in v1.3.8.

## Why this release exists

v1.3.8 added a per-peer header budget to stop a peer from replaying known
Etchash headers and burning `HashimotoLight` CPU. That budget charged every
header the same amount, which left a gap: post-activation Etchash headers are
one to two orders of magnitude more expensive to verify than RandomX/QHash
headers, so a single peer staying inside the flat budget could still consume
several CPU cores. v1.3.9 closes that gap and cleans up two latent sharp edges
found in the same audit pass.

## R1 — Etchash headers cost 10× in the per-peer header budget

`PeerManagerImpl::CheckHeadersPoW()` now charges the per-peer header budget by
algorithm instead of by header count:

- Etchash headers cost **10** units, every other header costs **1**.
- Etchash-only headers sync drops from ~2,000 to ~200 headers/s per peer.
- RandomX/QHash headers sync stays at ~2,000 headers/s per peer.

This is an **algorithm weighting hardening of the existing v1.3.8 budget**, not
a new rule: the budget itself (20,000-header burst, 2,000/s refill) is
unchanged, header continuity checks are unchanged, and the rate limit is still
only applied before `HasValidProofOfWork()`. Full verification still happens
exactly once per header in `AcceptBlockHeader()`.

The algorithm is resolved through `GetPowAlgoForHeader()` — the same predicate
the validation path uses — so the weight cannot silently drift away from the
bit-30 dispatch at height 21,000. The 10× factor is a heuristic and can be
retuned from mainnet observation without touching consensus code.

Normal multi-peer sync is unaffected: the budget is per peer, so a honest peer
that follows the chain normally never reaches it.

## Defensive cleanup (no behavior change)

- `GetDualAlgoWorkRequired()` now asserts `nActHeight > 0` before deriving the
  activation anchor. With `nDualAlgoActivationHeight = 0` the anchor lookup
  becomes `GetAncestor(-1)`, returns `nullptr`, and the old fallback would
  silently return `powLimit` — a chain with no difficulty at all. It now fails
  loudly instead. All current chains keep their values (21,000 on
  mainnet/testnet, 150 on regtest), so nothing observable changes.
- The testnet minimum-difficulty branch inside the dual-algo path documents
  why it intentionally keeps `2 * nPowTargetSpacing` rather than switching to
  the dual-algo spacing. On RCPU testnet/regtest that branch is a consensus
  rule, and changing the constant would move the trigger window from 600 s to
  1200 s and split v1.3.8 against v1.3.9 nodes. It is left untouched.

## Performance (mining)

`getblocktemplate` previously kept a single static template slot with a
`fCachedQhashTemplate` flag, so a miner alternating RandomX and Etchash
requests (two workers, or one pool polling both) triggered a full
`CreateNewBlock()` on every algorithm switch even when the tip and the mempool
had not moved. Each algorithm now has its own template slot. The invalidation
rules are identical — rebuild on tip change, on mempool update after 5 s, or on
failure — but evaluated per algorithm. `nTransactionsUpdatedLast` stays global
because `longpollid` watches mempool updates, not per-algorithm templates.

## Added: dual-algo reorg functional test

`test/functional/feature_dualalgo_reorg.py` mines past activation, invalidates
a post-activation block, rebuilds a competing branch with a different
RandomX/Etchash mix, and requires both nodes to converge on the same tip before
and after mining further mixed blocks. This covers the per-algo block count
cache and the height-aware `GetPowAlgoForHeader()` across a reorg, where the
Etchash/RandomX ratio changes and both ASERT instances have to be recomputed.

## Upgrade

- v1.3.9 is **recommended** for public nodes and for anything that relays
  headers after height 21,000.
- **Consensus-critical baseline is still v1.3.7**: nodes, pools and miners that
  validate bit-30 blocks at/after 21,000 must run the v1.3.7+ big-endian
  Etchash rule. v1.3.9 is built on v1.3.8, so it carries that rule.
- Companion versions remain: miner **1.0.23+**, Miningcore pool with the
  big-endian target and raw `etchash_seed_hash` patch.
- No coordinated upgrade window is needed. A v1.3.8 node and a v1.3.9 node
  agree on every block and every target.

## Compatibility

- No change to blocks, transactions, CT rules, wallet formats, RPC results
  (`getblocktemplate` returns the same schema and the same values for a given
  tip and mempool) or the Etchash result byte order.
- Asset names: `rcpu-1.3.9-*`.

## Verification

- Unit tests: `dualalgo_tests` 19/19 pass (ASERT KAT, powLimit boundaries, the
  per-algo count cache, `GetPowAlgoForHeader()`), and the rest of
  `test_bitcoin` passes.
- Functional: `feature_dualalgo_count_cache.py` (count cache rebuild after
  restart) and `feature_dualalgo_reorg.py` (new) pass.
- Host build verified on Windows/MSYS2-MINGW64 (`--enable-tests`, full
  `test_bitcoin` link). Linux verification is tracked separately — the changes
  touch no platform-specific code.
