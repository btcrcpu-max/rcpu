# RCPU Core v1.4.18 release notes

v1.4.18 closes one consensus edge case in the dual-algorithm difficulty
retarget, removes the spend key from new confidential addresses, and makes the
release verification tooling fail closed. Only the first item is a consensus
change, and it is height-gated.

## Consensus: first block of a never-mined PoW algorithm (POW-02)

Each algorithm keeps its own ASERT state and re-anchors when it has been idle
for more than `nDualAlgoReanchorGap`. The re-anchor condition required a
previous block of the same algorithm (`nLastSameHeight >= 0`), so an algorithm
that had **never** produced a block since activation never re-anchored: its
anchor stayed pinned to the activation block and its target stayed at
`powLimit` forever. The first block of that algorithm could therefore be mined
at the easiest possible difficulty, regardless of how much hash power had
joined since activation, and a reorg could inherit the same window.

From `nDualAlgoNeverMinedFixHeight` the node now treats "no block of this
algorithm yet, and the gap since the activation anchor exceeds
`nDualAlgoReanchorGap`" as a re-anchor: the anchor moves to the current height
and the target is clamped to at most 4x the pre-activation target
(`nDualAlgoMaxDrop / 2`), the same bound as a normal re-anchor.

### Activation height — the rule ships inactive

`nDualAlgoNeverMinedFixHeight` is `std::numeric_limits<int>::max()` in the
v1.4.18 source tree, so the new rule is **inactive** here: for difficulty,
v1.4.18 behaves exactly like v1.4.17. The code path, the 4x clamp and the unit
tests are in place, but no chain behaviour changes until the height is set.

Activation is scheduled in a follow-up release, which will pin the height to
`tip + 2016` at that time. **That follow-up is a mandatory upgrade**: v1.4.18
and older do not implement the re-anchor and will compute a different
difficulty for the first block of a previously unused algorithm, which splits
the chain.

The replay tool reproduces both the legacy and the fixed difficulty sequence
from a block list, so the activation height can be validated before that
release:

```
contrib/devtools/dual_algo_replay.py --never-mined-fix-height <height> ...
```

## Wallet: confidential addresses no longer expose the spend key (WAL-01)

`rcpux1...` addresses embed an ECDH blinding public key that recipients use for
path B/C outputs. That key used to be **the spend public key**, so handing out
an address for view-only purposes also handed out spending authority.

New addresses use payload version `0x01`, whose embedded key is
`HMAC-SHA256(spend secret, "rcpu/confidential-view-key/v1" || counter)`. The
derivation is one-way: the view key cannot be turned back into the spend key.

- `0x00` (legacy, blinding key == spend key) and `0x01` are both accepted.
- Unblinding tries the spend key first and then the derived view key, so every
  existing address, UTXO and wallet keeps working. **No wallet migration and no
  reindex.**
- New addresses are written as `0x01` whenever the private key is available.
  Watch-only descriptors and locked wallets fall back to `0x00`, which is still
  spendable and unblindable.
- The blinding key is used only on the send side; the on-chain script remains a
  plain P2WPKH for the spend key, so consensus, `IsMine` and script validation
  are unchanged.

A `0x01` payload cannot be authenticated against the witness program without
the spend private key, so a sender cannot distinguish a view key from an
arbitrary 33-byte public key. Bounding that requires a commitment inside the
payload and is a separate format change.

## Release verification (REL-01, REL-02)

`contrib/verify-binaries/verify.py` is now RCPU-specific and fail-closed:

- downloads only from `github.com/btcrcpu-max/rcpu/releases/download/v<version>/`;
- accepts a single pinned signer,
  `934D5BC95DD4B3ACFEF521B9547633501FE4B8EE`, and counts only trusted
  signatures (the previous threshold counted untrusted ones as well);
- treats a `SHA256SUMS.txt` entry without a local file as an integrity failure
  instead of printing `MISSING` and exiting 0;
- rejects `-unsigned` Windows artifacts unless `--allow-unsigned` is passed;
- requires at least one asset per platform (`--require-platforms`, default
  `linux,win`).

The publish job gains build provenance attestations and a read-back step that
compares the assets GitHub actually serves with the local files, rejects drafts
and zero-byte assets, re-downloads `SHA256SUMS.txt`, and verifies its detached
signature.

Reproducible builds are still not provided: that needs a pinned toolchain and a
second independent builder.

## Verification

```
gpg --verify SHA256SUMS.txt.asc SHA256SUMS.txt

git verify-tag v1.4.18
python3 contrib/verify-binaries/test.py
```

## Compatibility

- Consensus: the never-mined re-anchor is compiled in but inactive
  (`nDualAlgoNeverMinedFixHeight = INT_MAX`), so v1.4.18 consensus behaviour is
  identical to v1.4.17. No reindex required.
- Wallet: `0x00` and `0x01` confidential addresses are both readable; no
  migration.
- RPC: no interface change. `getaddressinfo` still reports
  `blinding_pubkey`, which is now the derived view key for new addresses.
